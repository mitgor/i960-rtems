# AcceleRAID 160 bounded stock-allocator probe

Status, 2026-10-16: **persistent flash and the bounded stock allocate/free operation passed on the new card.** The PC returned after a software reboot. The old DAC960PG `0000:37:04.1` remained unbound and untouched during every observed preflash, staging, and flash step.

The new 592-byte [handler](../../../host/accele160/allocator/handler.S) preserves accepted PING and fixed 80-byte RAM-call operations and adds operation 3. It calls the stock `c0066b90` allocator for one fixed 256 KiB mode-1 block with caller ID `0x96016003`, frees that pointer through stock `c0066fc0` with the same size and ID, and writes a four-word result only at `c000f820`. The host supplies only a nonzero nonce in a zero-DMA, 64-byte envelope. There is no host-controlled allocation size or pointer. A caller must compare the full stock allocator count/owner page before and after, restore the result slot, and leave any uncertain command module pinned.

The exact 1 MiB [candidate](candidate.bin) has SHA-256 `0124657ded5618f1a00737d4917a500bccbbeea951e3f1e33cee6d84799dd5d0`. It changes 484 bytes relative to accepted RAM-call firmware `1f13799b…c4aaf`, confined to the loader cave and two checksum words. The expanded runtime and boot block are unchanged. The 592-byte handler SHA-256 is `94d627e8…16169`, and `readelf -r` found no relocations. [Offline image audit](../../../host/accele160/allocator/audit.py) pins all binary inputs and exact output; four tests reject source-image mutation and tampered capture bytes.

On boot `bee73454-ba41-417b-9c32-ac1f436ee5e6`, a guarded preflash 1 MiB `READIMAGE` matched the accepted RAM-call image. `STOREIMAGE` staged the candidate, and a separate full `READIMAGE` returned the exact candidate SHA with status 0, residual 0 and guard changes 0. The one-shot `FLASHIMAGE` then completed after 37.045 seconds with status 0 and residual 0. Compact [live receipts](live/) preserve the command requests, status, ownership and hashes; the redundant full preflash and staged readback bytes remain in `/home/mit/i960-accele160-allocator-20261016/` on the PC. Post-boot persistence was established separately on the next boot.

On new boot `0796a44a-14be-4487-b22d-5191a1946e16`, the host returned after the software reboot. The custom driver required `raid_class` plus exact `read_bdf=0000:37:09.1` to bind; an early no-parameter insertion bound no card. The temporary driver override was cleared back to `(null)`. The exact-BDF `myrsread` binding, old-card unbound state and default PIATVR `c0000000` passed. Two independent same-boot guarded full-flash reads both equaled the candidate SHA with status/residual/guard changes zero before [the exact command module and session](../../../host/accele160/allocator/). The pinned Linux `6.8.0-138-generic` [module](allocator_command.ko) SHA-256 is `0a0d0e22…a1d85e`; the corrected [session executable](allocator_session) SHA-256 is `f8d842bc…96d1d5`. The session captures the full 4 KiB result page and allocator table page, checks the returned address lies in the known free mode-1 run, verifies the **256 count and 256 owner words** return byte-for-byte, restores the result slot, compares the whole loader page and restores PIATVR. [Replay verification](../../../host/accele160/allocator/verify_live.py) and deliberate tamper tests pass.

Both live calls returned `c0750000` for 256 KiB with status/residual zero. The first harness incorrectly compared the entire adjacent 4 KiB page: two bytes at offset `0xaa0`, immediately **after** the count/owner arrays, advanced as ordinary stock firmware state. Its command completed, but the companion was retained. A separate [finish tool](../../../host/accele160/allocator/finish_allocator_session.c) verified the actual 2 KiB allocator arrays and live result page, restored the 16-byte slot, restored PIATVR and released/unloaded the module without another card command. [First-call cleanup evidence](live/alloc-call-0/cleanup.json) preserves this distinction. The corrected second session completed and released normally; its [replay](live/alloc-call-1/replay.json) reports exactly 16 changed result bytes, identical allocator metadata SHA `8b49e75e…398c8b5f`, and an aligned pointer in eight previously free blocks. Later independent table snapshots retained that metadata SHA, a final loader page equaled the preimage, and a guarded post-call full-flash read still matched the candidate. Deliberate mutations of the result, unrelated page byte and allocator owner word are all rejected.

Even a successful 256 KiB allocate/free call proves only the stock allocator route. A retained owner-tagged grant, bounded chunk upload, cache handoff, STOP/timeout recovery, minimal RTEMS task, network transport and Doom remain separate gates. The largest free contiguous stock pool in the current map is 1,540,096 bytes, far short of Doom's 8 MiB arena; that needs a separately proven exclusive handoff or wider memory mapping.
