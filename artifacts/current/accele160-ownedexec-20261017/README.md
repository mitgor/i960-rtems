# AcceleRAID 160 exact leaf execution from owned RAM

Status, 2026-10-17: **persistent owned-RAM execution accepted.** The PC returned on boot `c2ff6769-876d-4aaa-974f-d47497e8f84d`. Two guarded complete flash reads matched the exact candidate before live calls. The old DAC960PG `37:04.1` remained unbound throughout.

The exact 1 MiB [candidate](candidate.bin) SHA-256 is `6f056a984d8e8d6fde6eb2001bddfd5ecc3b03918051c4d13e3cc4ab31480aa7`; it extends accepted digest image `665cb121…5c708a0`. The 2,280-byte [handler](../../../host/accele160/ownedexec/handler.S) SHA-256 is `b8647c4f…663afef`. It has no ELF relocations and changes only the loader cave and two checksum words; expanded runtime and boot block are unchanged. [Exact-image audit](../../../host/accele160/ownedexec/audit.py) reports 1,919 changed bytes and rejects modified inputs.

Operation 8 uses the zero-DMA `0x8f` mailbox envelope and fixed nonce `0x16161081`. It checks the retained owner record, bounds, fixed two-page count, expected FNV of all 8 KiB, and the exact first 80 bytes against the leaf embedded in the handler. It invalidates D-cache before inspecting PCI-written bytes and I-cache immediately before `callx` at the saved grant base. The exact leaf writes only the 16-byte result slot at `c000f800`, returns normally, and the handler checks its nonce, sum 496 and return value before reporting success. A separate control at `c000f880` has `EXEC`, nonce, count 2 and digest. FNV checks transfer integrity; exact payload comparison protects this proof's entry bytes.

The prepared [live harness](../../../host/accele160/ownedexec/run_ownedexec.py) pins the firmware, modules and 80-byte probe. It demands two independent same-boot full-flash reads, copies and checks pages 0 and 1 under one fixed 512 KiB stock owner, calls operation 7 for a contiguous digest, then operation 8 for the exact leaf. It retains resources on any uncertain status and restores staging, controls, result slots, loader page and allocator metadata after a normal return. The [replay verifier](../../../host/accele160/ownedexec/verify_live.py) passed on both live calls; synthetic and live mutation tests also pass.

Before programming, a guarded full-image read matched the accepted digest firmware, then STOREIMAGE and independent full-image readback matched this exact candidate with zero status/residual/DMA guard changes. FLASHIMAGE completed in 36.961 seconds with status/residual zero. Full data reads remain on the test PC; [compact command receipts](live/) and 4 KiB captures are archived here. This is not an RTEMS or Doom execution result.

## Live results

[Post-boot read 0](live/persistent-0/result.json) and [read 1](live/persistent-1/result.json) independently matched exact flash SHA `6f056a98…480aa7`; both had zero status/residual/DMA guard changes. The [first owned call](live/ownedexec-live/) copied two contiguous pages under stock owner `0x96016004` at `c0710000`, measured an 8 KiB card/host FNV `0x699d962b`, compared the exact leaf bytes and ran the leaf by `callx c0710000` after I-cache invalidation. It returned normally with nonce `0x16161081`, sum 496 and the expected XOR result. Card and host result records agreed. The staging page, all controls, loader page, PIATVR and all 512 allocator owner/count words restored; all five command companions unloaded. A [post-call full flash read](live/postcall-flash/result.json) matched.

[Wrong expected execution digest](live/ownedexec-bad-hash/) and [one-byte modified leaf immediate](live/ownedexec-bad-code/) each returned stock unsupported status 2 **before the call**. Both left the result and call-report sentinels unchanged and restored the allocation and loader state. The changed immediate is inside the leaf's `DONE` constant and would still permit normal return if called, so the rejection is a useful exact-code admission test. [Negative replay](../../../host/accele160/ownedexec/verify_negative.py) passed. Seven live positive-capture mutations to staging, copy, digest, result, report, unrelated loader bytes and owner metadata were rejected. A guarded [post-negative read](live/post-negative-flash/result.json) matched flash.

A [second successful call](live/ownedexec-repeat/) in a fresh grant on the same boot returned the same digest and nonce/result, passed independent replay, restored all state and unloaded all companions. The final [full flash read](live/post-repeat-flash/result.json) matched with unchanged DMA guards. Old `37:04.1` remained unbound.

This proves a fixed exact 80-byte leaf can run and return from stock-allocated RAM after a validated two-page upload. It does not yet prove arbitrary task code, a relocated RTEMS image, interrupts/timer on this board, persistent resident task lifetime, 512 KiB upload at scale or Doom's 8 MiB arena.
