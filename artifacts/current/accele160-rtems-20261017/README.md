# AcceleRAID 160 bounded RTEMS software-clock acceptance

Status, 2026-10-17: **accepted on the new card `0000:37:09.1`; old DAC960PG `0000:37:04.1` stayed unbound.** This is a one-shot RTEMS 4.6.6 task/scheduler proof. Ten synchronous software ticks woke a worker at tick five, then RTEMS returned normally. It does **not** establish a hardware timer, interrupt-driven preemption, independent host STOP, networking, web service or Doom.

The [new-board source](../../../rtems/accele160/README.md) links at `c0710000`. The flat [kernel](build/kernel.bin) is **57,972 bytes**, including **34,672 bytes BSS** through its image tail; [manifest](image/manifest.json) pads it to **15 pages / 61,440 bytes**. BSS ends at `c071e270`, below the last staging page `c078f000`. The `c0710000..c078ffff` stock allocator grant leaves 112 other payload pages. The [padded image](image/padded.bin) SHA-256 is `318b9f70fe021ce1fb18e3c75465d9231cb55c3ca6893d99511b9b73c383adc0`; its FNV is `0x648486da`. The ELF has no unresolved relocations. Exact source, symbol map, ELF, build metadata and pinned Linux command module are retained here and in `rtems/accele160/` / `host/accele160/rtems_gate/`.

The exact [1 MiB candidate](candidate.bin) SHA-256 is `68451b38b96609fa3a95eb9497fe85a34ac92fec45b912c53612969b1209a988`. [Offline audit](../../../host/accele160/rtems_gate/audit.py) checks the stock and preceding flashed image identities, cave preimage, changed-byte scope, loader/trailer checksums, unchanged expanded runtime and boot block, and exact candidate hash. The 2,888-byte handler SHA-256 is `b3481994f9539489c65921b1fc914741d4aee09d4e53279f0b778b4269b13d19`; it has no ELF relocations. This candidate changes 2,449 bytes relative to the accepted op-8 image, only in the loader cave and two checksum words. Four mutated audit inputs were rejected offline.

[Preflash full read](live/preflash-current/result.json) matched the op-8 firmware SHA `6f056a98…480aa7`. [STOREIMAGE](live/stage/result.json) and the independent [staged full read](live/staged-readback/result.json) matched the new candidate with zero status, residual and DMA-guard changes. [FLASHIMAGE](live/flash/result.json) completed in **36.98 s** with status/residual zero. The PC restarted from boot `c2ff6769…` to `ccdf3abd…`; the exact `myrsread` driver was bound to the new BDF while the old card remained unbound. Two independent [post-boot full reads](live/persistent-0/result.json) and [read 1](live/persistent-1/result.json) matched the candidate byte-for-byte, each with zero status/residual/DMA-guard changes.

The first [live capture](live/live-0/) uploaded **15 × 4,096 bytes** in **1.143 s** under one fixed stock owner record. Each page had host readback and card-side copy/FNV validation; the card's whole-image FNV matched. Wrong expected hash and page count 14 returned stock unsupported status 2 with both report slots unchanged. Operation 9 then admitted the pinned image, invalidated D/I caches, called `c0710000`, and returned a fixed eight-word report: `RTEM`, nonce `0x16161091`, RTEMS result `0x46600006`, done `1`, worker wake tick `5`, tick variable `11`, BSS end `c071e270`, marker `0x1600a001`. The host observed **0.05094 s** for the command cycle; this includes roughly 50 ms status polling and is not the RTEMS CPU runtime. Full loader page, staging page, PIATVR and all allocator owner/count words restored before releasing the grant. [Post-call full read](live/postcall-flash/result.json) matched.

A [second fresh-grant run](live/live-1/) repeated the same result: **1.183 s** upload and **0.05091 s** observed RTEMS command cycle. The final [full read](live/post-repeat-flash/result.json) matched. All four post-boot full flash reads have the same boot ID and exact candidate SHA. No one-shot command module remained loaded; the old card stayed unbound.

[Independent replay](../../../host/accele160/rtems_gate/verify_live.py) passed both live captures, every page/control/result, both rejection statuses, entire loader-page comparisons, staging restoration, reserve/release metadata and all four complete post-boot flash reads. Five mutations per capture (middle staged byte, copy result, RTEMS report, owner metadata, rejected status) were refused. The on-card FNV and exact 80-byte prefix are admission checks for this trusted-host experiment; they are not a secure arbitrary-code signature. An unreturned RTEMS call would retain command/owner resources and require reboot investigation. No such failure occurred in either accepted run.

Next hardware gate: identify and reserve AcceleRAID-specific timer/vector/mask resources, add independent bounded STOP, then extend the runtime toward host-backed IPv4/IPv6. The old DAC960PG networking and Doom binaries remain board-specific and were not loaded.

A subsequent [read-only stock-ROM timer literal scan](timer-static.json) looked for seven candidate timer/interrupt register constants in the stock expanded runtime and copied loader. It is a static triage aid only; no timer register was read or written on the live card. The [next clock/STOP gates](../../../rtems/accele160/TIMER-NEXT.md) spell out the inventory, timer ownership and independent sideband-control tests.
