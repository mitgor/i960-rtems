# Exact four-sample plane-span experiment

`--span-four --fast-render` adds a four-sample prefix to the accepted two-sample
packed-coordinate span kernel. The old two-sample and one-sample tails remain.
The switch is opt-in and recorded through engine/platform/admission/play
manifests. Default two-sample r_draw.o matches the previous accepted plain build
byte-for-byte. No quality reduction, transport change, audit reduction or flash
write. Physical acceptance uses fixed low detail; high-detail primitive tests
are not a high-detail gameplay acceptance.

## Reproduction

The isolated SSH workspace is `/home/mit/i960-span-four-20261016`.

copy the pinned `artifacts/doom-m1-20261011/doomgeneric-source.tar.gz` and

workspaces. Per-build engine/platform/kernel manifests preserve exact commands.

Run `primitive.sh`, `check_builds.py`, `native.py --baseline`, `native.py` before

Never run this automation against somebody else's retained card session.

## Build and offline checks

Each primitive variant passes 123,264 scalar-oracle cases under host32 ASan/UBSan:
high/low detail, all destination alignments, counts 0–320, random coordinates
and explicit zero/extreme step/position values, wrap, and sentinel preservation.
Both native builds pass two deterministic 52-frame runs with STOP/heap drain;
all native pixels/palettes match the earlier accepted C-column reference.

The candidate uses ordinary RAM word stores only when aligned, byte stores
otherwise; unsigned arithmetic retains exact wrap. The generated loop uses
registers, with no stack spill/call in the inner kernel. `objdump -Dr` is used
because `-dr` incorrectly reports some instructions at local-symbol boundaries
as out of bounds in this old toolchain.

`r_draw.o` text grows 4,224 → 4,528 bytes (+304), data/BSS unchanged.
Admission grows 819,152 → 819,488 bytes (+336), below the 900,000-byte limit.
Protected O0 point-side and exact-divide objects retain their accepted hashes.
Only r_draw.o, the combined engine, and the two source-path-dependent assertion
objects r_data.o/w_wad.o differ; those latter sources are identical. Both final
links have no undefined symbols. [Build checks](build-checks.json).

The final baseline is substantially faster than the first (6.814 versus 6.431).
The first three runs alone suggested a small gain, but excluding A2 would
cherry-pick the result. All four windows of A2 are faster, not just one outlier.
The baseline binary/image/module hashes, options, detail mode, mailbox-to-DMA
transition and framebuffer addresses match across repeats. The nominal IRQ
period remains about 10,000.08 microseconds. No active parallel card work was
found. [Captured checks](repeatability-check.json). These checks do **not** prove
identical cache or scheduling state; the cause of the faster repeat remains
unresolved. Do not claim either a causal kernel speedup or a reliable 2.54%
regression from this batch. Keep the candidate available for controlled
follow-up, and keep two-sample spans as the default.

Completion-observed → HTTP availability measured **5.0736 → 4.3934 ms**.
Transport code was unchanged; this is an observation, not evidence that the
span kernel optimized delivery, and it is not browser paint latency.
