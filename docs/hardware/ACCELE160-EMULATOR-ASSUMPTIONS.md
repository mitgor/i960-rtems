# AcceleRAID 160 five-reply replay: model assumptions and falsification plan

Updated 2026-11-16. Scope: the saved second-spare stock image versus the native five-reply image, through the modified QEMU/i960 interpreter and Alpine guest login. The [stock `0x2d` capture](../../artifacts/current/accele160-stock-ioctl2d-20261116/README.md), [native coupled gate](../../artifacts/current/accele160-native-ioctl2d-coupled-20261116/README.md), and [Linux login gate](../../artifacts/current/accele160-native-linux-guest-20261116/README.md) are valid **within this model**. They do not reproduce the HP Z400 pre-beep failure.

## Assumption ledger

| Layer | Model behavior used by these gates | Evidence and limit | Discriminator |
| --- | --- | --- | --- |
| i960 reset | The interpreter decodes the saved 80303 reset record, uses generic sim5 `resetAt(entry, prcb)`, and supplies `--board-id=11` on reads of `0xe0400000` until firmware writes it. It treats flat RAM/flash mappings and several CSR reset states as modeled memory. | The selector value came from a post-boot observation, not a measured reset-time read. The stock reset block's real DRAM, flash-bank, clock and PCI timing are not reproduced. See `runner.cc` reset setup and `NativeCore.cc` board selector. | Measure the selector, flash fetch, reset release, DRAM and PCI command state at power-on on the stock spare. Sweep selector values offline and record the first stock/native divergence rather than assuming 11 is universal. |
| Board peripherals | The startup UART-presence probe at `0xe0600007` reads zero; DMA channel status has a bounded software model with no general hardware DMA engine. The first 64 host mailbox bytes and output buffer have special low-address backing. | A special host-memory region lets native code read `0x9f120` and reply to `0x9f3e0`; it is not a demonstrated physical ATU translation. `NativeCore.cc` explicitly labels this as exploratory. | Validate 80303 ATU window, DMA1 descriptors/status, cache coherency, and low host-memory visibility with a recoverable live measurement or a bus analyzer before relying on ROM replies on hardware. |
| Stock QLogic ISP | The preboot harness enables timer, QLogic PCI and a chain of ISP mailbox acknowledgments. The model accepts a fingerprinted uploaded ISP 10.01 RISC image but **does not execute ISP RISC instructions**. It supplies version, queue, retry, reset-delay, active-negation, feature, zero status, init-ID, bus-reset and target-sweep acknowledgments. | These are guarded stubs in `NativeCore.cc`, not independent chip behavior. The `0x001f` MB1/MB2 zero reply is explicitly a hypothesis. Stock scans and resulting controller-info bytes depend on those responses. | Remove one acknowledgment at a time and record the first stock stall; capture real ISP mailbox registers/queue producer and scan results on a stock card, then replace only measured stubs. |
| Stock absent-device scan | `test_preboot_card.py` stages 15 incomplete/no-device responses into modeled ISP queue memory, or invokes an automatic guarded queue model. The default capture path writes response words and producer/status registers directly. | The five stock reply fixtures match in repeated **synthetic** runs, not a physical no-disk scan. The real card may discover different bus/device states. | Repeat stock capture under the guarded automatic queue mode; compare each response and ROM reply. Capture actual stock scan status/response queue on an idle physical spare. |
| Stock IRQ routing | The default preboot path clears a pending i960 bit and injects vector `0x42` with diagnostic bridge command `J 42` for each of 15 responses, bypassing the unmodeled external router. Some alternatives use an explicit PIRSR bit-0 override and routed `E 0`. | The success of a stock trace under forced vectors does not prove that an unmodified 80303/ISP board routes those interrupts. Priority is checked in the injection path, but the source is invented. | Run without `J 42` and without PIRSR override; failure should be attributed to the routing gap. Measure PIRSR, IMAP, IPND/IMSK and ISP ISR/SEMAPHORE under stock startup. |
| Host PCI model | QEMU exposes measured `8086:2962` bridge and `1069:0050` RAID identities, revision and 8 KiB BAR. PCI command writes to both functions are mirrored into i960 `0x1004/0x1204`; the x86 ROM's ACK-status write is provisionally mapped to i960 inbound doorbell bit 1. | Identity/BAR were read from the live stock card. Mirrored command semantics and ACK-to-doorbell mapping are partial. Other 80303 PCI configuration side effects, arbitration and reset-time timing are not modeled. | Record actual early host PCI config transaction order, command bits, BAR accesses and MU status on stock hardware; use those traces to gate model sequencing. |
| MU bridge and completion | QEMU DMA-reads a 64-byte guest mailbox and sends `M` to the i960 socket. The model latches message words, doorbell and status; native firmware polls these registers and uses modeled DMA1 output. QEMU steps the i960 in bounded instruction chunks, reads local outbound message/doorbell and copies the payload into guest RAM. | The five native completions are byte-exact against synthetic stock fixtures. The socket, stepping schedule, low-memory backing, and QEMU guest-RAM copy are software mechanisms; no physical timing, cache or interrupt transport is shown. The native path calls routed `E 7` but does not require its returned vector. | Withhold PCI bus-master/readiness, corrupt mailbox length/address/ID, remask MU, vary stepping schedule, and check no completion. Then measure physical MU/ATU/IRQ/DMA behavior before cold-boot confidence is raised. |
| x86 BIOS and guest | A patched SeaBIOS supplies the Mylex PCI BDF to its legacy boot callback; standard SeaBIOS's zero argument made the ROM return early. QEMU boots Alpine from an IDE CD-ROM and detects `localhost login:`. | This demonstrates ROM handoff to a generic Linux boot, not HP `786G3 v03.15` behavior, `myrs` attach, or RAID I/O. The five-reply QEMU model is opt-in and only recognizes captured request shapes. | Probe the guest's PCI and driver state, then attempt a bounded `myrs` attach with no virtual disks. On hardware, capture HP POST checkpoints/PCI events; SeaBIOS success is not a POST proxy. |

The separate `--explore-rom-ioctls` zero-filled synthetic QEMU mode is a control case only. It fabricates completion without i960 firmware and must never be counted as a native or stock completion. The five-reply native/Linux gates explicitly reject stock or synthetic completion lines.

Stock and native runs submit the same five captured ROM mailbox shapes and produce the same response bytes in this absent-device scenario. Their controller-side paths are different: stock reaches mailbox service only after the stubbed QLogic scan and IRQ injections, while the current native ROM diagnostic answers the five requests directly and does not initialize a physical ISP or enumerate disks. The fifth `0x2d` payload is the same card's 512-byte descriptor, which is stable across the two stock captures; that does not establish other fields as hardware measurements.

## Focused negative result

The new [readiness test](../../rtems/accele160/emulator/test_native_readiness_negative.py) submits the exact first ROM mailbox to the native five-reply image **without** host PCI command readiness. Despite a modeled MU doorbell and CPU stepping, no reply or completion appears. Adding only the boot doorbell still leaves it pending. After both PCI command words are set to `0x107`, the same pending mailbox completes with command ID `0x7f`. The [saved result](../../artifacts/current/accele160-model-assumption-audit-20261116/readiness-negative.txt) passed locally. This tests a real gate in native firmware, but the method of supplying those command words remains a model assumption.

## Later memory-ring extension

The [second offline batch](../ACCELE160-NEXT-TEN-OFFLINE-STEPS-2.md) extended the model beyond the five ROM mailboxes. It observed stock `SET_MEM_MBOX` setup and three memory-ring replies, then matched those bytes with opt-in native RTEMS handlers. The [strict guest mirror trio](../../artifacts/current/accele160-native-followup-mirror-pair-20261116/receipt.json) rejects output unless the native i960 report, DMA1 EOC, status, doorbell, ring slot, bounded dynamic guest DMA address, stock payload hash, and untouched guest destination agree. Linux reaches two [new ring slots](../../artifacts/current/accele160-native-next-boundary-20261116/README.md), but `myrs` probe does not finish.

The stock payloads in this extension still depend on the synthetic no-device QLogic scan and the QEMU guest-memory bridge. The guest mirror copies model-local output into guest RAM after checks; it is not a model of physical 80303 ATU translation, cache coherency, PCI bus arbitration, or timing. Neither the first-ring gate nor the later mirror runs exercises the HP Z400 firmware that failed before beep. The [third batch](../ACCELE160-NEXT-TEN-OFFLINE-STEPS-3.md) retains these assumptions and requires new stock evidence before adding replies for the new slots.

The third batch reached a sharper QLogic boundary. For Linux's SCSI(10) INQUIRY, stock firmware posted a type `0x09` ISP request IOCB with matching CDB/data DMA and advanced the ISP request producer from 30 to 31. The modeled ISP response producer and consumer stayed at 15; no sense, data, status-ring entry or outbound doorbell appeared within 20 million i960 steps, after which Linux requested reset. The [forensic receipt](../../artifacts/current/accele160-stock-next-static-20261116/slot4-isp-boundary-receipt.json) establishes a missing modeled ISP response, not a stock SCSI reply or a physical hang. A native INQUIRY completion needs independently justified ISP/target behavior before it can be implemented.

## Next falsification order

1. Make the stock boot reach the same scan milestone without forced `J 42` by using measured routing state; report the first missing vector/register rather than patching over it.
2. Compare stock replies under manual and guarded automatic absent-device queue modes, including their full DMA bytes and completion status. A difference invalidates a single hard-coded response fixture.
3. Vary the i960 reset selector and modeled PCI readiness/ACK timing; identify whether the native first request still completes and whether stock reaches MU unmask. Preserve all failed traces.
4. Exercise MU/DMA negative cases: invalid output address/length, wrong command ID, masked inbound status and delayed output ACK. The native implementation must remain bounded and fail closed.
5. Probe Linux `myrs` attach separately from Alpine login. Require driver request/response traces and no invented disks; a login prompt alone only proves the IDE guest booted.
6. On return to physical access, follow the [read-only hardware audit](ACCELE160-POST-FAILURE-AUDIT.md) before any new flash. The first spare's exact programmed bytes and pre-beep failure remain the dominant unresolved evidence.
