# AcceleRAID 160 pre-beep failure: evidence and next physical measurements

Updated 2026-11-16. This is an offline audit of saved evidence, not a flash approval or a claim that QEMU predicts the HP Z400. The object is the **first spare** programmed with the initial native RTEMS image; the **second spare** remains the known stock reference. The original working card remains a separate reference.

## Established observations

| Observation | What it establishes | Limit |
| --- | --- | --- |
| Before the first flash, two independent 1 MiB reads of the first spare agreed, SHA-256 `fadd2b0f6ed9bb88d7c846edd235e5e222cbe3a990b694115c5fa66170e7a816`. The candidate retained that card's descriptor and stock reset block. | The source stock image and intended layout are known. | The packer's unchanged regions do not prove startup behavior. |
| The FLASHIMAGE command returned zero status/residual; the later external-programmer read was byte-identical to the intended 1 MiB native image, SHA-256 `6f16d71310d75937b5f3961b1faae81eab3258a29371c8505d788c50c545e3bd`. | An incomplete or wrong flash write is an unlikely cause of the observed failure. | Only one programmer read has been reported; chip identity/orientation and read repeatability were not independently rechecked. |
| The HP Z400 failed before the usual beep with the first programmed spare installed and booted after its removal. | The failure is associated with that card/image installation. | No POST checkpoint, PCI trace, i960 UART, or flash-bus trace locates the stopping point. |
| With HP Slot 6 option-ROM download disabled, both Mylex boot BIOS procedures disabled, and SATA RAID option ROM disabled, a stock second spare in Slot 6 plus the original card in Slot 5 booted Linux. Replacing only the Slot 6 card with the programmed first spare again stopped before beep. | Ordinary two-card occupancy and the configured Slot 6 option-ROM setting alone do not explain the failure. | The setting was not independently verified by a ROM-fetch trace. HP may inspect or initialize the card before or without executing its expansion ROM. |
| The exact failed image reaches RTEMS `PASS` in the exploratory i960 interpreter; early stock/native host-state comparison shows the old native diagnostic parks before producing stock's later board context and PCI/interrupt readiness. | There was a known missing host-facing startup implementation in the first image. | The interpreter's reset selector and MMIO behavior are partly inferred, so this does not prove that missing runtime caused the physical hang. Later native candidates address some mailbox behavior but are not physical-test qualified. |
| Two new second-spare [diagnostic images](../../artifacts/current/accele160-minimal-diagnostic-20261116/README.md) show `SGT2` → `ENT0` → `ENT1` → RTEMS/PASS in the interpreter. The service image preserves four stock-matched ring replies in a paired Debian guest gate. | The instrumented entry markers and bounded host service are reproducible offline. | Markers live in volatile card DRAM. If HP hangs before exposing the PCI BAR, an external flash programmer cannot read them; physical POST, PCI or card-side instrumentation is still needed. |

Evidence: [first spare flash and programmer read](../../artifacts/current/accele160-spare-rom-20261025/README.md), [Slot 6 experiment and host-state comparison](../../artifacts/current/accele160-second-spare-20261026/README.md), [offline workplan](../ACCELE160-OFFLINE-WORKPLAN.md), [flash bridge brief](ACCELE160-FLASH-BRIDGE-PCB-BRIEF.md).

## Failure hypotheses and decisive observations

| Hypothesis | Present assessment | Discriminator |
| --- | --- | --- |
| Firmware lacks early PCI/MU/interrupt service required by HP POST. | Plausible: the first native image parked at `PASS`, while stock later initialized host-facing state. | Capture a POST checkpoint or PCI bus trace with stock and failed card; identify the first host register read/write or timeout that diverges. A card-side UART/debug port at first RTEMS entry would separate pre-entry from runtime failure. |
| i960 reset, DRAM, flash fetch or power-on timing differs from the interpreter model. | Open. Stock reset block was preserved, but its handoff to the replacement main firmware may depend on state not modeled. | High-impedance flash-bus trace from power-on on stock and failed card, plus rail/reset measurements. Record first differing fetch or command and whether RTEMS entry is reached. |
| The card holds the primary PCI interface in configuration retry (added 2026-11-17). | Leading candidate, not physically confirmed. Intel documents that an 80303 in mode 3 retries every configuration cycle until firmware clears EBCR bit 2; stock clears it in its runtime (`c0052df4`, EBCR = `0x48`, then `BIOS Cfg Wait...`) and the native images never do. It fits the failure before the beep, the indifference to the option-ROM setting and the byte-exact flash. In the offline model the failed image stalls the host on its first configuration read and stock does not. See the [experiment](../ACCELE160-EBCR-RELEASE-EXPERIMENT.md). | Read EBCR on the stock card (`setpci -s 37:04.0 40.w`, expect `0048`). A POST-code card with the failed spare installed should stop in PCI enumeration. A native image that releases retry at stage-two entry should let the PC boot and reports the reset value of EBCR in its `PCI0` record. |
| Host x86 option ROM executes and waits forever. | Weakened by the Slot 6 disabled experiment, not eliminated. The actual HP firmware's early card handling is untraced. | A read-only bus/POST trace that distinguishes expansion-ROM fetch/entry from earlier PCI enumeration; compare with option-ROM setting on and off while the **stock** spare boots. |
| Wrong, partial, or cross-card flash contents. | Strongly weakened by one exact programmer read and per-card descriptor preservation. | Repeat full external-programmer read of the first spare; compare both reads to pinned failed and stock hashes. Verify the second spare's two stock reads remain identical before ever deriving a candidate from it. |
| Electrical/card damage independent of firmware. | Open. A programmer read proves stored bytes, not that all interface timing and signals remain healthy. | After two saved reads, restore the first spare's **own** stock image externally, independently read it back, and cold-boot it in Slot 6 under the recorded BIOS settings. This is a later recovery experiment, not part of the read-only measurement visit. |
| Card-specific descriptor or board variant mismatch. | The first candidate kept its own descriptor; the two spare stock images differ only in their descriptor region. No mismatch is established. | Pin each physical card to serial/photo, PCI address and full-image SHA. Never use a different card's 1 MiB image as its recovery/candidate base. |

No percentage of cold-boot success is justified by the current QEMU run. The modified SeaBIOS and synthetic ISP responses are explicit model assumptions, while the observed failure is on HP `786G3 v03.15`.

## Next visit: read-only collection order

The [return-to-hardware collector](../../host/accele160/offline_return/README.md) implements the host-inventory capture and an explicit optional two-read guarded workflow described below. It has not been run on the remote PC.

1. **Preserve the known booting configuration.** Keep the original card in Slot 5 and the unmodified second spare in Slot 6. Photograph the card labels/positions and HP BIOS settings. Record whether `Slot 6 Option ROM Download` and both Mylex boot BIOS options are still disabled. Do not insert the failed spare for this baseline.
2. **Record a clean stock boot.** Save boot ID, HP BIOS/board version, exact PCI function identities and topology (`lspci -Dnn`, `lspci -Dvv -s 0000:37:04.0`, `lspci -Dvv -s 0000:37:04.1`, and the corresponding `37:09` functions), BAR/ROM decode state, kernel log around `myrs`/PCI, and whether both controllers remain free of storage devices. These commands inspect host state; do not enable expansion-ROM decode by writing PCI config space.
3. **Reconfirm the second spare's stock bytes only if the known guarded reader is available.** Run two separate full 1 MiB READIMAGE captures bound solely to `0000:37:04.1`, after checking the BDF/identity. Each must return zero status/residual/guard changes, release the module, and hash to `0ca0f4b6dd08d2f71102c6dbb174dfd1b151bce53f943bc571f66a85c9d6e943`. Treat any mismatch or unexpected command status as a stop condition. READIMAGE is a controller command, even though it does not program flash; use the existing guarded workflow rather than improvising register reads.
4. **Independently read the failed first spare's chip twice with the external programmer, off the card and unpowered.** Record chip marking, orientation, programmer model/voltage, size, both hashes, and a byte comparison. Expected failed-image SHA is `6f16d71310d75937b5f3961b1faae81eab3258a29371c8505d788c50c545e3bd`. Save both raw dumps before any restore or write.
5. **If instruments are available, scope only the stock spare at power-on.** With high-impedance probes, record card/flash VCC, `RP#`, `CE#`, `OE#`, `WE#`, `RY/BY#`, and `VPP` plus a POST checkpoint/PCI trace if the equipment supports it. Establish stock first-fetch timing and whether startup issues Intel flash commands. A probe that adds appreciable load can itself break the boot; document probe type and loading.

Do not change the BIOS settings between a stock baseline and a later comparative boot without recording it. Do not infer ROM execution merely from PCI expansion-ROM decode flags observed after Linux starts.

## Candidate decision gate for one spare

A later physical experiment should use a single explicitly identified spare. Before any new flash, require: (a) two matching current full stock reads from that spare; (b) an image packed from that same card's stock base, with a machine-readable diff showing only intended firmware region changes; (c) reproducible source/toolchain build hashes and a passing ROM/native coupled gate; (d) a verified recovery image and external programmer procedure; (e) a measurement that narrows the first pre-beep failure, ideally RTEMS-entry/POST/PCI/flash-bus evidence; and (f) an explicit cold-boot test and rollback sequence. The decision should say which uncertainty remains and why the planned test is useful. The [first-ring offline gate](../../artifacts/current/accele160-native-ring-offline-gate-20261116/README.md) now passes and the two stock follow-up replies are captured, but neither this model result nor the direct native follow-up gates establishes HP cold-boot behavior. Current candidates do **not** meet the physical decision gate.
