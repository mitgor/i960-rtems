## Address trap and next work

`37:09.1` now names the **new** card, not the tested DAC960PG. The existing dump
module defaults to that BDF but its PCI match table accepts only `1069:0010`.
Several transport launch/cleanup scripts also hard-code `37:09.1`. Do not change
PCI IDs or reuse firmware/register addresses merely to make the new card bind.
The old board can be targeted only after explicit BDF/identity checks are updated.
Its patched ROM was not re-read in this inspection.

The new controller uses `myrs` and different firmware/device IDs; the current
DAC960PG loader and RTEMS transport are not yet validated for it. Next: make
board selection explicit, inventory the new controller's firmware and register
interface, and obtain/validate its own stock firmware backup before any patching.
Then prove bounded RAM upload/execution and timer/DMA ownership before Doom or
clock comparisons. The old board remains installed for reference.

This inspection did not bind/unbind drivers, read MMIO, enable the expansion ROM,
write firmware, start our runtime or change disk/controller configuration.
Half-height development remains on hold.
