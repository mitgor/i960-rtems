# AcceleRAID 160 bounded RTEMS hardware clock

**Accepted on the card, 2026-10-17.** The unchanged stock-coexisting operation-13 firmware admitted a 17-page RAM image from its owned 512 KiB grant. RTEMS created a worker, timer 1 generated hardware interrupts at the configured 10 ms tick, and the worker woke after five ticks. A valid sideband STOP, following a rejected stale token, ended the worker; a second path exhausted a fixed 500,000-poll budget without host input. Both paths returned through the firmware callback after masking and draining timer 1 and restoring the cached vector, mapping, mask, timer registers and firmware stack. No firmware write was made.

The image uses 15 pages for code/data/BSS, page 15 for the ISR's C stack, and page 16 for the entry stack and hardware interrupt frame. The ISR saves all global registers and writable trace controls before switching to its owned stack. It calls `rtems_clock_tick()` with `_ISR_Nest_level` and `_Thread_Dispatch_disable_level` raised, then defers scheduling to a task boundary. The worker runs at interrupt priority 0 during its bounded CPU loop; this test **does not** prove unrestricted ISR-driven task preemption or a resident RTEMS service. The host's even-page PCI aperture cannot validate the entry-stack bytes, so the card-side stack pointer is bounded and the odd ISR-stack page is read directly.

The preflight requires exact stock ICON, maps, mask, cached vectors, timer-1 count/reload/mode and **timer-1 pending bit**. Stock timer 0 can have pending bit `0x1000` while RTEMS starts with interrupts masked; this is preserved and does not invalidate ownership of timer 1 (`0x2000`). The worker and cleanup do not clear the stock timer-0 bit. The accepted code uses an initialized read/write operand for i960 `modpc` priority changes (`+r` with mask `0x1f0000`). Earlier experimental code used an output-only operand and silently left the worker at priority 31. The accepted worker trace records actual PC priority 0, active interrupt mask `0x2000`, map `0x00180000`, reload 125,000 and continuing ticks.

Two complete STOP/no-host batches passed under boot ID `2fef3a5a-8027-4067-9d7e-2a8f8f6c6b84`. STOP took **100.506/100.299 ms** host-observed, including the five-tick wake; stale STOP remained pending. The no-host path took **555.830/558.102 ms**, with **52 ticks** and the exact 500,000-poll budget each time. Firmware SP was `c0002100` before and after; ISR C SP was `c071f100`. The owned cached vector was restored to `0xaaaaaaaa`. Six paired full 1 MiB firmware reads had SHA-256 `1c4995ada54f944265c11f346177708351b4ff5a1003ba232f7e39b6a74b89bd`; all status, residual and guard-change fields were zero. Independent register/vector inventories after each batch matched stock. The loader page, staging source and all 512 allocator count/owner records were restored; no one-shot command module remained loaded. The old DAC960PG stayed unbound and untouched.

The accepted image SHA-256 is `d7234b9309e5e435456ddd50905787b4ddbab4e7fd9e0ea18d5094ca09a39db5`; kernel SHA-256 is `b592bc5a711e6847cc208cc9753e9b672940d17d0c2c2e7c9c3f328f3e695150`; whole-image FNV is `0x7b154664`. Exact binary, map, source snapshot and evidence are in [the current artifact](../../../artifacts/current/accele160-autoclock-20261017/README.md). To replay the full acceptance and four tamper cases locally:

```sh
python3 rtems/accele160/autoclock/verify_live.py artifacts/current/accele160-autoclock-20261017
python3 rtems/accele160/autoclock/test_verify_live.py artifacts/current/accele160-autoclock-20261017
```

To reproduce the binary on the test PC, run `build.sh RTEMS_BUILD_DIR TOOLCHAIN_BIN OUT_DIR` with the pinned RTEMS core and toolchain described in [the preceding task lease](../lease/README.md). The physical `run_autoclock.py` requires exact file identities, two same-boot full flash reads, the new card bound to `myrsread`, the old card unbound, no block device, and a stock descriptor. It checks per-page copies, whole-card digest, READY/STOP/ACK, all owner records and bounded stack evidence. It retains the grant and module on any uncertain result. Do not force-unload a pending operation-13 module; use the narrowly guarded recovery scripts only for an already returned and byte-matched call.

The investigation recorded three useful failures. The first host checker tried to validate an even grant page through an unreadable PCI path, then [guardedly recovered](recover_finished.py) the already completed call. A 10 ms candidate with yields passed STOP but its long no-host path returned status 2 and required reboot; it is not accepted. A later exact diagnostic showed the preflight rejected unrelated stock timer-0 pending bit `0x1000`, and another recorded worker PC priority 31 while timer-1 pending accumulated. The corrected timer-1-only guard and initialized `modpc` operand produced the accepted repeated result. Previous experimental binaries were pruned; their source snapshots and key captures remain in the artifact.

The next gate is an owned, bounded task-switch/preemption test on this board, followed by a finite resident lease and independent STOP path that can quiesce non-cooperating code. Networking and Doom need their own RAM and transport admission; the 17-page proof is not a deployment profile.
