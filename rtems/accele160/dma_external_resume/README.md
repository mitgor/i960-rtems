# External recovery of a held AcceleRAID DMA transfer — candidate

The next gate asks whether an independent host process can resume a channel-0 transfer after the original owner dies while the channel is deliberately suspended. It uses the exact new-card BDF, the same pinned 4 KiB payload and guards, the stock-owned 512 KiB RAM grant, 13,000 finite descriptors, and full RTEMS/owner/flash audits. `app.c` consumes STOP when it suspends, publishes `DMA_HELD`, accepts an exact sideband `RESUME` token no earlier than 80 timer ticks after suspension, and otherwise resumes itself at 200 ticks. Both routes still require normal descriptor completion before pin/grant release. The host starter dies with `SIGKILL` after saving the held checkpoint; `recover.py` independently checks that the PID is gone, denies early release, sends the token only for a still-held session, and audits terminal state before cleanup. The 200-tick fallback prevents a lost recovery process from leaving this *test* indefinitely suspended; it is not a cancellation mechanism.

**Status, 2026-10-17: not yet accepted.** The first image `28b679b9…` reached `DMA_HELD` and killed its host owner, but I launched recovery after the fallback had fired. It safely kept the pin and grant while uncertain. A revised recovery audited the normal completed transfer, exact payload and guards, owner/page/stage, RTEMS shutdown and channels, then released resources. Its final trace records STOP/suspend tick 21, fallback resume tick 221, completion/terminal tick 248 and reason 2. Four full-flash reads before and after matched stock SHA-256 `1c4995ada54f944265c11f346177708351b4ff5a1003ba232f7e39b6a74b89bd`. Because the HALT word was still present, the worker stopped immediately after fallback completion; this is a **negative control**, not external-resume acceptance.

The corrected image `f0228b6a…` consumes HALT at suspension so an external RESUME can lead to the tick-300 no-host expiry. Its first attempt was rejected *before DMA submission*: the starter compared channel 0 against an older accepted run rather than the immediately preceding fallback completion. The trace recorded `dma_state=0xdead0002`; the guarded runner retained the pin and grant. A reboot cleared that test allocation. On the resulting warm boot, the new card remained unbound despite loading exact `myrsread`; one advertised PCI PM reset while unbound succeeded but did not make driver initialization bind. A full power cycle is needed before further card work. The old card stayed unbound and untouched.

Both scripts contain exact path and identity gates; inspect those paths before reuse on another host.
