# External recovery of a held AcceleRAID DMA transfer — accepted gate

This gate tests whether an independent host process can resume a channel-0 transfer after the original owner dies while the channel is deliberately suspended. It uses the exact new-card BDF, the same pinned 4 KiB payload and guards, the stock-owned 512 KiB RAM grant, 13,000 finite descriptors, and full RTEMS/owner/flash audits. `app.c` consumes STOP when it suspends, publishes `DMA_HELD`, accepts an exact sideband `RESUME` token no earlier than 80 timer ticks after suspension, and otherwise resumes itself at 200 ticks. Both routes still require normal descriptor completion before pin/grant release. The host starter dies with `SIGKILL` after saving the held checkpoint; `recover.py` independently checks that the PID is gone, denies early release, sends the token only for a still-held session, and audits terminal state before cleanup. The 200-tick fallback prevents a lost recovery process from leaving this *test* indefinitely suspended; it is not a cancellation mechanism.

**Status, 2026-10-17: accepted for this bounded finite transfer.** The corrected image `f0228b6a…` reached `DMA_HELD`, its original host PID was killed, and a separate recovery process observed that PID absent and an early pin release denied with `EBUSY`. Recovery wrote the RESUME token; the card resumed at tick 101 after suspending at tick 21, before its tick-200 fallback, and reached its tick-300 terminal state with reason 1. All exact payload/guard, DMA-channel, owner/page/stage, RTEMS/context and resource-release audits passed. Two full 1 MiB flash reads before and two after matched stock SHA-256 `1c4995ada54f944265c11f346177708351b4ff5a1003ba232f7e39b6a74b89bd`. The old card stayed unbound and untouched. [Accepted capture](../../../artifacts/current/accele160-dma-external-resume-20261017/README.md) and `verify_accepted.py` replay this result; two tampered captures were rejected.

The earlier image `28b679b9…` reached `DMA_HELD` and killed its host owner, but recovery began after the card's fallback resumed at tick 221 and completed at tick 248. It was fully audited and released, but is only a negative control. The corrected image consumes HALT at suspension. Its first attempt rejected stale prior channel state before DMA (`dma_state=0xdead0002`) and retained the pin and grant until reboot. I then misdiagnosed an unbound driver: I had omitted mandatory `read_bdf=0000:37:09.1` from `myrsread` insertion. Reloading with that parameter bound the card immediately. The PCI PM reset attempt does not establish any hardware initialization fault. The later full power cycle provided the clean boot used for acceptance; it was not proven necessary for binding.

For reproduction, bind exact `myrsread` with `read_bdf=0000:37:09.1`, confirm no test modules, run `run_preflight.sh` for two full reads and fresh channel inventory, then run `run_live.sh` **as root** so independent recovery follows the deliberate `SIGKILL` immediately. Both scripts contain exact path and identity gates; inspect those paths before reuse on another host. Require reason 1, completed channel 0, exact payload/guards, ownership and RTEMS audits, and post-run paired full-flash matches. Preserve the pin and grant on any uncertain result; never force-unload them.

This software-held gate still cannot establish safe release after a genuinely erroring or never-draining PCI transaction. A later hardware reset/fault gate needs its own exact reset boundary and buffer-retention proof.
